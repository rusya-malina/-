# Модульная архитектура Telegram-бота

Бот теперь собирается из небольших функциональных модулей. `bot.py` отвечает только за запуск процесса, health endpoint и корректное завершение. `app_factory.py` создаёт Telegram Application, подключает фоновые задания и регистрирует маршруты.

| Модуль | Ответственность |
|---|---|
| `config.py` | Пути файлов, окружение и предметные константы без зависимости от Telegram. |
| `states.py` | Все состояния ConversationHandler без бизнес-логики. |
| `data_models.py` | Canonical schema v1, constructors и backward-compatible readers для users, groups, заявок, teams и issuance. |
| `errors.py` | Typed `StorageError`, `DataValidationError` и `ExternalServiceError` для единых error boundaries. |
| `bot_context.py` | Только обратная совместимость для старых тестов и модулей; новый production-код использует явные импорты. |
| `storage.py` | Асинхронное чтение, атомарная запись JSON-файлов, single-file и multi-file lock операции, планы и pending-заявки. |
| `keyboards.py` | Reply-клавиатуры и callback-разметка меню, включая подтверждение выдачи. |
| `services.py` | Общие расчёты остатков, нормализация имён, уведомления и фоновая проверка заявок. |
| `handlers/user.py` | Регистрация, расчёты LAS/LAU, смена имени и возврат в главное меню. |
| `handlers/admin.py` | Пользователи и удаление сотрудника. |
| `handlers/teams.py` | Выбор команды и подтверждение администратором, KPI и остатки команды через единый реестр. |
| `handlers/requests.py` | Единый inbox: регистрация, выбор команды и произвольные заявки пользователей; принятие и отклонение из раздела «📥 Заявки». |
| `handlers/kpi.py` | Ручной KPI, планы, просмотр KPI, справочник и личные остатки через единый реестр сотрудников. |
| `handlers/issuance.py` | Меню выдач, выдача MINTS/стиков, подтверждение и статистика. |
| `handlers/uploads.py` | Excel-загрузка KPI и Excel-загрузка выдач. Тяжёлая обработка остаётся изолированной от меню. |
| `handlers/broadcast.py` | Рассылка текста и фотографий. |
| `health.py` | Минимальный `/healthz` endpoint для Render. |

### Единый реестр сотрудников

`organization.py` собирает канонический список сотрудников из `users.json`, `groups.json`, KPI и выдач. Записи с одинаковым нормализованным ФИО объединяются; числовой Telegram ID имеет приоритет над сервисным `excel_*` ID, а все идентификаторы сохраняются как `aliases`. Личные KPI, личные остатки, KPI команды и остатки команды используют этот реестр. Выдачи по всем алиасам сотрудника суммируются, поэтому импортированные Excel-записи больше не создают отдельные строки в командной отчетности.

Пользовательская клавиатура содержит кнопку «📝 Оставить заявку». Текст заявки сохраняется в `user_requests.json`, а администратор видит её вместе с регистрационными и командными заявками в разделе «⚙️ Дополнительно → 📥 Заявки». Для старых записей с названием «К LAMP» при запуске выполняется миграция на «R LAMP».

## Что показали логи Render

В логах не было Python traceback. Процесс стартовал, scheduler выполнял задания каждые пять минут, а примерно через пятнадцать минут Render записал штатную последовательность `Application is stopping`, `Scheduler has been shut down` и `Application.stop() complete`. На панели также показано предупреждение, что бесплатный инстанс засыпает при отсутствии входящих запросов.

Следовательно, разделение исходного файла улучшает сопровождение и уменьшает связанность, но само по себе не отключает сон бесплатного Render-инстанса. Для этого workflow health-check обновлён с интервала 15 минут до 10 минут и дополнен защитой от параллельных запусков. В рабочей версии polling также использует `bootstrap_retries=5`, чтобы спокойнее переживать краткий конфликт при handover после перезапуска.

## Проверки

Перед публикацией выполняются компиляция всех `.py`-файлов, Ruff с единым `ruff.toml`, архитектурный contract-тест, миграционный тест схем, typed storage error test, импорт всех модулей, создание Telegram Application с тестовым токеном, проверки клавиатур, расчёта остатков, регистрации, единого реестра сотрудников, конкурентного хранилища, наличия обоих Excel-обработчиков и поведенческие аудиты. Эти же проверки запускаются в `.github/workflows/quality.yml` на push и pull request.

Одобрение регистрации использует `storage.update_many_json()` с упорядоченной блокировкой файлов `pending_requests.json`, `users.json` и `groups.json`; это предотвращает параллельные обработчики, которые видят разные версии одной заявки. Для одиночных хранилищ используется `update_json()`, а синхронное чтение клавиатур и startup-миграций проходит через `load_json_sync()`. При старте `migrate_json_schemas()` переводит legacy-значения в schema v1, сохраняя совместимые readers для уже существующих тестовых и внешних snapshots.

## Группы и регистрация

После очистки `users.json` пользователь проходит регистрацию в порядке: выбор одной из групп `A LAMP`, `R LAMP`, `coor A`, `coor R`, `SPV`, `MNG`; ввод имени; ввод фамилии; подтверждение администратором. Заявка хранится в `pending_requests.json` с полями `name`, `group` и `created_at`. Подтверждённые группы хранятся в `groups.json`. При отказе заявка удаляется, а пользователю снова отправляется клавиатура выбора группы без повторного ввода имени и фамилии.

| Группа | Главное меню | Раздел «Мой KPI» |
|---|---|---|
| `A LAMP`, `R LAMP` | Новый расчет, Мой KPI, Справочник KPI, Остатки | KPI и Часы |
| `coor A`, `coor R` | Новый расчет, Мой KPI, Справочник KPI, Остатки | Только KPI |
| `SPV`, `MNG` | Новый расчет, Мой KPI, Справочник KPI | Только KPI |
| Администратор | Текущее админское меню без изменений | Админские права сохраняются |
