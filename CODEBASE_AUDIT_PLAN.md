# Согласование архитектуры бота

## Исходное состояние

Проект работоспособен: базовые аудиты, ролевые сценарии, отчётность, регистрация и тесты согласованности проходят. Однако код действительно собран из нескольких независимых слоёв. Главный источник скрытых конфликтов — `bot_context.py`, который одновременно служит конфигурацией, импорт-барабаном для библиотек, контейнером состояний диалога и местом инициализации логирования.

Ruff обнаружил 91 предупреждение. Значительная часть связана с 18 wildcard-импортами, неиспользуемыми импортами, широкими `except Exception`, блокирующим чтением файлов внутри async-кода и несогласованными прямыми операциями с JSON. Эти предупреждения не следует исправлять механически: сначала нужно сохранить поведение, затем убрать скрытые зависимости.

## Целевая архитектура

| Слой | Ответственность | Правило |
|---|---|---|
| `config.py` | Пути файлов, окружение, идентификатор администратора и константы предметной области | Не импортирует Telegram и pandas |
| `states.py` | Состояния ConversationHandler | Не содержит бизнес-логику |
| `telegram_types.py` или явные импорты в модулях | Типы и Telegram-классы | Каждый модуль импортирует только используемые им классы |
| `storage.py` | Асинхронное чтение, атомарная запись и сериализованные read-modify-write операции | Обработчики не делают небезопасный load-изменить-save для конкурентных данных |
| `organization.py` | Единый реестр сотрудников, группы, права видимости и объединение алиасов | Все отчёты используют один реестр |
| `services.py` | Расчёты, уведомления и чистые предметные функции | Не содержит маршрутизацию Telegram |
| `handlers/*` | Только сценарии Telegram и подготовка ответов | Не дублируют правила идентификации и хранения |
| `app_factory.py` | Явная регистрация маршрутов и состояний | Нет wildcard-импортов |
| `tools/tests` | Регрессии и проверки поведения | Общие фикстуры вместо повторяющихся заглушек |

## Приоритеты

Первым шагом будут устранены скрытые импорты и разделён контекст на конфигурацию и состояния. Вторым шагом будет стандартизирована запись JSON для пользователей, групп, заявок, команд и выдач. Третьим шагом будет унифицирована обработка ошибок и блокирующих операций. После каждого набора изменений запускается полный текущий набор тестов, чтобы не менять поведение незаметно.

## Ограничения безопасности

Рефакторинг не меняет Telegram-токен, Render-настройки, GitHub-секреты или рабочие JSON-данные без отдельной необходимости. Существующие пользовательские данные считаются источником истины и должны быть сохранены. Любая миграция формата выполняется обратимо и с резервной копией.
